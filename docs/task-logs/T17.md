## Design summary

Full design: `docs/superpowers/specs/2026-08-19-t17-telegram-consent-stop-killswitch-design.md`.
Full plan: `docs/superpowers/plans/2026-08-19-t17-telegram-consent-stop-killswitch.md`.

Telegram's Bot API has no chat-history-read method for bots, so inbound
consent/STOP handling can only work via `getUpdates` polling with a
durably-stored offset cursor — a different mechanism from WAHA's approach,
which is why this needed its own design pass rather than reusing T16
machinery.

- **`SCHEMA_V8`** (`database.py`): three new tables/concerns — a
  `sending_control` singleton row (enabled/disabled flag, optional
  `DisableReason`, timestamp), a `sending_control_events` audit trail
  (append-only, one row per enable/disable transition), and a
  `telegram_inbound_offset` cursor for `getUpdates` polling. Five new
  `Database` methods: `is_sending_enabled`, `disable_sending`,
  `enable_sending`, `get_telegram_inbound_offset`,
  `set_telegram_inbound_offset`. A `DisableReason` enum
  (`STOP_COMMAND`/`BLOCKED_BY_USER`/`ADMIN_KILL_SWITCH`) records *why*
  sending was disabled, for the audit trail and for future admin tooling.
  A `recipient_key_for_chat_id` helper derives the delivery idempotency key
  deterministically from the enrolled `chat_id`, closing the T16b-flagged
  gap where `recipient_key` and the real destination were never
  structurally tied.
- **`consent.py`** (new): `poll_inbound_stop` — polls Telegram's
  `getUpdates` from the stored offset, advances the offset past every
  message it sees (whether or not it matches), and calls
  `disable_sending(DisableReason.STOP_COMMAND)` only when an inbound
  message's `chat.id` matches the enrolled recipient's `chat_id` *and* the
  message text is an exact `STOP` (case handling per the design spec — not
  a fuzzy match). A pure `_process_updates` helper carries the actual
  matching logic so it's testable without network I/O. `TelegramPollError`
  wraps polling failures (bounded read, chunked response, non-2xx, timeout)
  without leaking the bot token into any error string, mirroring
  `sender.py`'s existing bounded-I/O precedent.
- **`sender.py`**: a new `SenderBlocked` exception, raised when Telegram's
  403 response body indicates the specific "bot was blocked by the user"
  condition (not any generic 403 — those still fall through to the
  existing `SenderRejected` classification). A fix round
  (`85f1c47`) widened the detection's `except` clause to also catch
  `UnicodeDecodeError` on a malformed body, so a bad byte sequence can't
  crash the classifier and produce an unhandled exception instead of a
  safe `False`.
- **`delivery.py`**: `run_daily_send` gates on `is_sending_enabled()`
  *before any production or network work* — including before an
  already-`RESERVED` delivery is allowed to progress, so the admin kill
  switch (or a STOP received mid-flight) stops a send that already claimed
  its row. A new `except SenderBlocked` handler calls
  `disable_sending(DisableReason.BLOCKED_BY_USER)` on the specific
  blocked-by-user 403, durably turning off future sends without owner
  intervention. A fail-closed assertion ties the caller-supplied
  `recipient_key` to the enrolled `chat_id` via `recipient_key_for_chat_id`
  — a mismatch is a hard rejection, not a pass-through, closing the T16b
  gap.
- **AST trust-boundary test** (`test_voice_enrollment_boundaries.py`):
  extended so `discovery/`, `generation/`, and `judging/` still cannot
  reach `consent.py` (by construction — `consent.py` has zero coupling to
  those modules; the test enforces this structurally, not just today).

## Independent review

Independent whole-branch security review complete, performed by a fresh
subagent on the most capable available model against the full `main..HEAD`
diff (10 commits), independent of any per-task review context. It traced
the branch's core security properties directly against source rather than
this log's prose: exact case-sensitive/untrimmed STOP matching with a
short-circuited non-enrolled-chat guard, the `SenderBlocked`/`SenderRejected`
except-clause ordering, the `recipient_key`/`chat_id` assertion's placement
before any mutation, `disable_sending`/`enable_sending`'s real
`BEGIN IMMEDIATE` transactional idempotency, restart durability through a
second `Database` instance, the additive-only `SCHEMA_V8` migration, zero
`discovery`/`generation`/`judging` coupling to `consent.py`, and no
secrets in the diff. Zero Critical findings — the reviewer could not
construct a path that sends while disabled, bypasses STOP, or leaks a
secret.

Four Important findings, all confirmed real defects (not plan/reviewer
disagreements) and fixed in one fix wave, then re-reviewed clean by a
scoped re-review:

1. **Stranded reservation while disabled**: `reserve_next_message` ran
   unconditionally before the disabled-sending gate, so a kill-switched or
   STOPped system still reserved a fresh `QUEUED` message into `RESERVED`
   and stranded it permanently (no `RESERVED -> QUEUED` transition exists).
   Fixed: `is_sending_enabled()` is read once and gates the reservation
   call itself, while the existing-delivery lookup path (needed by the
   `SENDING`-crash-recovery and `DELIVERY_UNKNOWN`-terminal branches, which
   must always run) stays unconditional.
2. **Unpropagated sibling fix**: `consent.py`'s `getUpdates` body parsing
   only caught `json.JSONDecodeError`, missing `UnicodeDecodeError` on
   non-UTF-8 bytes (the identical defect class Task 3's fix round already
   closed in `sender.py`, never carried over). Fixed with the same
   `except ValueError` widening plus a unit test on `b"\x80abc"`.
3. **Missing red test**: no test drove `run_daily_send` through a real
   blocked-by-user 403 end-to-end to prove `disable_sending(BLOCKED_BY_USER)`
   actually fires — a listed T17 red test that no single per-task review
   could see, since it spans Tasks 3 and 4. Fixed with a new e2e test
   reusing the existing local fixed-status-server pattern, asserting both
   `MessageState.FAILED` and `is_sending_enabled() is False`; skips cleanly
   without `T13_VOICE_SAMPLE`/`T16B_TELEGRAM_SETTINGS` like its six
   siblings in the same file, matching this project's existing e2e-gating
   convention.
4. **Boundary coverage gap**: the AST trust-boundary test forbade importing
   `consent.py` but not the three new `Database` control methods
   (`disable_sending`/`enable_sending`/`is_sending_enabled`) as attribute
   names, short of the design spec's literal requirement. Fixed by adding
   the three names to `FORBIDDEN_ATTRIBUTE_NAMES`.

Five Minor findings were triaged and deferred with recorded reasoning
(ledger has full detail): an oversized-403-body edge case that degrades
safely; `poll_inbound_stop`'s HTTP wrapper has no non-credentialed fast
test (mirrors existing `sender.py` precedent); a one-line comment
suggestion on the disabled-gate's placement relative to the
`DELIVERY_UNKNOWN`-terminal branch; the design spec's own schema text
(nullable `reason`, plain `INTEGER PRIMARY KEY`) should be corrected to
match the implementation, which is the correct version; and a small
constant duplication between `consent.py` and `sender.py`, accepted under
this project's Karpathy rules (two call sites doesn't justify a shared
module).
