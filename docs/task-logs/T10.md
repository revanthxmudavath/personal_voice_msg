## Model/API/client pin (verbatim, from this plan's Global Constraints)

- Model pin (owner-confirmed for T10, independent of T09's benchmark-only
  pin): `gemini-3.6-flash`.
- Client: hand-rolled `aiohttp` HTTP boundary, not the `google-genai` SDK
  (removed after T09; not reintroduced).
- Endpoint (verified with a real call, 2026-08-04):
  `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`,
  auth via `x-goog-api-key` header — never in the URL, never logged.
- `generationConfig.temperature = 0.2` (plan text: "low temperature").
- `generationConfig.maxOutputTokens = 2048`.
- `generationConfig.responseMimeType = "application/json"`,
  `responseSchema = {"type": "OBJECT", "properties": {"sentence": {"type": "STRING"}}, "required": ["sentence"]}`.
- The real response's actual sentence is a JSON string inside
  `candidates[0].content.parts[0].text` — a second `json.loads()` is
  required.
- Any `candidates[0].finishReason` other than `"STOP"` is a hard reject.
- Generation receives only `InspirationCard.theme`, `.emotion`, `.imagery`,
  `.tone` — never `.source`, `.evidence`, `.discovery_timestamp`, or
  `.rights_category`.

## Harness

- `evals/t10/corpus.yaml` — 100 fixed `{theme, emotion, imagery, tone}` rows,
  generated deterministically by `evals/t10/generate_corpus.py` (kept in the
  repo for reproducibility; not imported by the provider or Promptfoo
  config, and not part of the qualification run itself). The rows are the
  first 100 entries, in fixed nested-loop order (`theme` outermost, `tone`
  innermost), of the 4×4×4×4 = 256 cross product of
  `personal_voice_msg.discovery.inspiration`'s `Theme`/`Emotion`/`Imagery`/`Tone`
  enums.
  - **Deviation from `task-4-brief.md`'s Step 2 phrasing**: the brief's own
    text says both "use every `Theme` value at least once" and "cycl[e]
    through the 4×4×4×4 cross product and tak[e] the first 100 in a fixed,
    reproducible order" — these two instructions are mutually exclusive
    (the first 100 rows of that exact nested order only ever reach 2 of the
    4 `Theme` values: all 64 `appreciation` rows, then the first 36
    `affection` rows; `companionship` and `encouragement` never appear).
    The task's explicit clarification instructions (received alongside the
    brief) resolved this ambiguity in favor of the literal nested-loop/
    first-100 rule, and that is what `generate_corpus.py` implements. Noted
    here for the record, not silently resolved.
- `evals/t10/provider.py` — Promptfoo custom Python provider. For each row,
  builds the matching `InspirationCard` (fixed, non-secret placeholder
  `source`/`evidence`/`discovery_timestamp` — generation never reads those
  fields), creates a fresh temporary SQLite file via `tempfile.mkstemp`
  (deleted after the trial, never a production or shared database), and
  calls the real `generate_sentence()` boundary from Task 3 against the
  real Gemini API using `load_gemini_settings()`. Returns the validated
  sentence text on success, or a clearly-labeled `T10_QUALIFICATION_FAILURE:
  <ExceptionType>` string on `SentenceValidationError` (which already
  subsumes `GeminiClientError`/malformed-response failures inside Task 3's
  own `generate_sentence`) — never raises uncaught, per Promptfoo's Python
  provider protocol.
- `evals/t10/promptfooconfig.yaml` — fixed provider (`file://provider.py`,
  pinned to the project's own venv Python so `personal_voice_msg` imports
  correctly), fixed corpus (`file://corpus.yaml`), and `defaultTest`
  assertions mirroring Task 3's own deterministic checks (non-empty output,
  no `http`/`www.` substring, exactly one terminal-punctuation mark at the
  end, and no `T10_QUALIFICATION_FAILURE` marker — so a labeled failure is
  always counted as failed by Promptfoo's own pass/fail summary, not only
  by out-of-band inspection). No `cache` default; `--no-cache` was passed
  at run time.

## Cheap pre-flight checks (not part of the paid 100-trial run)

Per the cost-awareness constraint, the provider and config were shaken out
with a small number of direct-Python real calls *before* wiring up
Promptfoo, so the paid 100-row run was not spent on debugging:

1. Three direct `generate_sentence()` calls (bypassing Promptfoo entirely)
   against three representative cards — all three produced accepted,
   structurally valid sentences.
2. One direct `provider.call_api()` call reproducing Promptfoo's exact call
   signature — this caught a real bug: the temp SQLite file was being
   deleted (`finally: temp_path.unlink(...)`) *before* the provider read the
   generated sentence back out of it, so every trial through the full
   `call_api` path failed with `sqlite3.OperationalError: no such table:
   messages`. Fixed by moving the cleanup to only run after the fetch
   completes.
3. One more direct `provider.call_api()` call after the fix — succeeded,
   returning a real accepted sentence.
4. One direct `provider.call_api()` call with a deliberately invalid
   `theme` value (no real API call — a `ValueError` is raised inside
   `Theme(...)` before any network request) — confirmed the provider's
   broad exception handler returns a labeled failure string with an
   `error` key and never raises uncaught.

Total real API calls spent on pre-flight validation: 4 (well within "2-3
manual test rows," rounded up by one to also exercise the exact
`call_api`-path bug that a pure `generate_sentence()`-only test would not
have caught).

### The one failure

| Field | Value |
|---|---|
| `theme` | `affection` |
| `emotion` | `joy` |
| `imagery` | `quiet_garden` |
| `tone` | `reassuring` |
| Provider output | `T10_QUALIFICATION_FAILURE: SentenceValidationError` |
| Promptfoo result | failed assertions (no terminal-punctuation match; contained the failure marker) |

`generate_sentence()` raised `SentenceValidationError` for this trial. By
design, `personal_voice_msg.generation.sentence.SentenceValidationError`
**never carries the rejected candidate text or the specific violated rule**
— its docstring is explicit: "Report a rejected generated sentence without
including its text." Internally, `generate_sentence` raises exactly this
same exception both for structural violations caught by
`validate_generated_sentence` (empty, URL/`www.`, missing or misplaced
terminal punctuation, or — had `source_text` been supplied, which it was
not in this synthetic-corpus run — a source-copy match) *and* for any
`GeminiClientError`/malformed-response failure from the client boundary
(non-`STOP` `finishReason`, bad JSON, HTTP failure). Both are intentional
fail-closed paths, not bugs.

**This failure is recorded honestly as-is; no redacted regression fixture
was added.** Reasoning: the brief's instruction is to add a fixture "if the
failure reveals a gap Task 3's validation missed." This failure does not
reveal a gap — it demonstrates the fail-closed path firing correctly on a
real trial, exactly as Task 3's existing `tests/fast/test_generation_sentence.py`
parametrized cases (`empty`, `whitespace-only`, `multi-sentence`,
`no-terminal-punctuation`, `https-url`, `www-url`,
`six-consecutive-source-words`) already unit-test each individual
structural rule that could produce this exact exception type. Fabricating
a specific sentence-text fixture for a category this evidence cannot
actually identify would misrepresent what was observed. No change to
`tests/fast/test_generation_sentence.py` was made.

### Scope note: source-copy checking was not exercised in this run

The corpus rows are synthetic `{theme, emotion, imagery, tone}` combinations
with a fixed placeholder `source`/`evidence` (no real scraped source page),
so `generate_sentence()` was called without `source_text=`, and
`validate_generated_sentence`'s `copies_source_span` check was consequently
never exercised by this harness (the check is skipped entirely when
`source_text is None`). This matches T10's own scoping: the qualification's
job is to empirically validate the generation boundary's structural
correctness and real-API behavior at volume; the source-copy rule itself is
already covered by Task 3's existing unit tests
(`test_rejects_six_consecutive_source_words`) with a real matched-source
fixture. Not a gap in this run — a deliberate, already-covered exclusion.

### One regression found and fixed: `scripts/repository_policy.py`

Installing `promptfoo` (Step 1) creates a `node_modules/` tree with roughly
500 packages directly under the repo root. `scripts/repository_policy.py`'s
`repository_files()` walk (`root.rglob("*")`) had no exclusion for
`node_modules` — only `.git`, `.mypy_cache`, `.pytest_cache`,
`.ruff_cache`, `.tmp`, `.uv-cache`, `.venv`, and `__pycache__` were excluded.
The first full `pytest -m fast` run after installing `promptfoo` (before
this fix) took **27m 44s** and had exactly one failure:
`tests/fast/test_repository_policy.py::test_secret_scan_accepts_current_repository_documented_fixtures`,
whose underlying `repository_policy.py secrets --root .` subprocess call
returned `4294967295` (i.e. `-1`, an abnormal external termination) with
empty stdout/stderr — consistent with the secrets scanner choking while
walking thousands of `node_modules` files.

Fix: added `"node_modules"` to `EXCLUDED_DIRECTORIES` in
`scripts/repository_policy.py` — the same treatment already given to
`.venv`, `__pycache__`, and `.uv-cache` (other dependency/build
directories). This is a one-line, directly-caused, in-scope fix (Step 1 of
this task creates `node_modules/`; nothing else in this task touches
`scripts/repository_policy.py`'s behavior). After the fix, the secrets
policy check alone completes in well under a minute, and the full
`pytest -m fast` rerun completed in **~41s** with **378 passed, 110
deselected**, no failures.
