## Design summary

Same-shaped internal sender boundary, transport swapped from WAHA/WhatsApp
to the Telegram Bot API:

- **`sender.py`**: WAHA's `POST /api/sendVoice` (`chatId`/`session`/base64
  file, `X-Api-Key` header) replaced with Telegram's `POST
  https://api.telegram.org/bot<token>/sendVoice` (`chat_id` + multipart
  `voice` upload, response gated on `payload["ok"]`). The
  `SenderRejected`/`SenderAmbiguous` taxonomy is preserved but reclassified
  around Telegram's actual status codes: an **explicit allow-list**
  (`{400, 401, 403, 404, 429}`, not a range check) maps to `SenderRejected`
  (safe to retry); everything else — any other status, a malformed body, a
  connection-level failure, no response at all — maps to `SenderAmbiguous`
  (must not retry blindly). No parameter can select a recipient; the
  destination is always `settings.telegram_chat_id`.
- **`config.py`**: `waha_base_url`/`waha_token`/`waha_session`/`recipient`
  removed entirely; `Settings` gains `telegram_chat_id: SensitiveValue[int]`
  and `telegram_bot_token: SensitiveValue[str]`. No configurable base URL —
  Telegram's endpoint is a fixed constant, unlike WAHA's self-hosted,
  loopback-validated one.
- **`recipient_enrollment.py`** (new): a one-time, owner-run, file-based
  enrollment step (`enroll_recipient(bot_token, destination, profile) ->
  int`) — polls `getUpdates` once, captures the enrolled recipient's
  `chat_id`, writes it immutably. Refuses to run if the destination already
  exists.
- **`delivery.py`**: the reconciliation subsystem is gone — Telegram's Bot
  API has no chat-history-read method for bots, so there is nothing to poll
  for a delayed confirmation. `DELIVERY_UNKNOWN` is now a genuinely
  terminal state for the Pacific day: `run_daily_send` returns immediately
  on entry with no network call possible, proven by tests that pass
  `session=None` (any code path that tried to send would raise
  `AttributeError` before the assertion).
- **Recipient identity vs. delivery routing decoupled**: `run_daily_send`'s
  idempotency boundary is the caller-supplied `recipient_key`, while the
  real destination is `settings.telegram_chat_id` — the two are never
  structurally tied together. Not a live gap today (no production caller
  of `run_daily_send` exists yet), but flagged as a T17 precondition: when
  the scheduler is wired, `recipient_key` must be derived from or asserted
  against the enrolled `chat_id`.
- **Inbound STOP/kill-switch handling** is explicitly out of scope for this
  plan (T17's territory) — see "Next step" below.

## Independent review

Required — T16b is on `AGENTS.md`'s mandatory independent-security-review
list (same posture as T15, T16). Two reviews were run, both by fresh
subagents with no implementation context, both told explicitly to verify
claims against actual current source rather than trust this plan's or any
report's prose:

**Re-review of Task 7's own fix** (sonnet, scoped to `a602274..e2217ea`):
confirmed the `run_daily_send`/`api_base` fix genuinely closes the
untested-`SenderAmbiguous`-branch gap, no new breakage, no other
`run_daily_send` call site affected (the new parameter is keyword-only
with a safe default).

**Whole-branch review** (opus, deep-scrutiny pass, given `AGENTS.md`,
`IMPLEMENTATION_PLAN.md`'s T16b section, the design spec, the full plan,
and the complete 12-commit diff `7c3fd2f..e2217ea`): verdict **CHANGES
REQUIRED**, 3 Important + 6 Minor findings.

Confirmed clean by direct source tracing (not the review's prose alone),
covering the review's 6 mandated focus areas:
- **Duplicate-send safety**: every `MessageState` entry point into
  `run_daily_send` traced; `send_voice_note` has exactly one production
  call site (`delivery.py`'s `AUDIO_READY` branch); `SENT` is genuinely
  terminal at the schema level (`DELIVERY_TRANSITIONS[SENT] = set()`,
  enforced pre-transaction-commit); concurrent calls are serialized by
  `BEGIN IMMEDIATE` plus a `WHERE state = <current>` guard, and a second
  layer of protection exists via the sender-nonce replay table.
- **Fail-closed status classification**: only the exact `{400, 401, 403,
  404, 429}` set yields `SenderRejected`; a mid-body connection drop,
  malformed/oversized JSON, and every connection-level error all yield
  `SenderAmbiguous` — confirmed by real-socket tests, no mocks.
- **Recipient enrollment immutability**: the accepted Task 2 characterization
  (TOCTOU/atomic-write minors, low risk given a one-time owner-run
  operation) still holds.
- **Trust boundary**: the AST test's actual logic (not its name) was read
  directly — see Finding C below for the real gap found here.
- **`DELIVERY_UNKNOWN` terminality**: enforced by an unconditional early
  `return` in `run_daily_send`, placed above every branch that could send;
  `reconcile_delivery` and its helpers are genuinely deleted repo-wide.
- **Secret handling**: the bot token travels only in the request URL path;
  the one exception handler around the Telegram POST call raises a fixed
  string (never `str(error)`), so no aiohttp connector-error message
  (which can embed the URL/token) ever surfaces. `SensitiveValue`
  redaction and `Settings.redactor()` cover all four new secret-shaped
  fields.

**3 Important findings, all confirmed against current source by the
controller (not the reviewer's prose alone) and fixed in one bundled round
(commit `e570e68`), re-reviewed clean (sonnet, scoped to
`e2217ea..e570e68`)**:

- **A — secret scanner had no Telegram detection.**
  `scripts/repository_policy.py` had no filename/content rule for Telegram
  bot tokens, and its sensitive-artifact-name list still only had the old
  WAHA-era `recipient.json`, not the new `telegram_chat_id.json`
  enrollment artifact — a real regression of the exact scanner that caught
  real dev secrets during T15. Fixed: added a `TELEGRAM_BOT_TOKEN` content
  regex (`\b\d{8,10}:[A-Za-z0-9_-]{35}\b`), added `telegram_chat_id.json`
  to the sensitive-artifact set, added a `"telegram" in filename and
  "token" in filename` clause, wired the new regex into the content-scan
  loop. Three new test cases each independently exercise a distinct code
  path (artifact-name match, filename substring, content regex).
- **B — recipient enrollment picked the last inbound message, not the
  first as the approved spec requires, with no ambiguity guard.**
  `recipient_enrollment.py`'s `_extract_chat_id` used `messages[-1]`; the
  design spec and `IMPLEMENTATION_PLAN.md` both specify the **first**
  inbound message — a drift introduced when this plan's own Task 2 section
  was written and faithfully transcribed by Task 2's implementer (not
  their bug). More importantly: since Telegram bots are discoverable by
  public `@username`, a `getUpdates` batch containing messages from more
  than one distinct `chat.id` (a stranger messaging the bot) was silently
  resolved to one chat_id with no signal anything was wrong — violating
  this project's fail-closed doctrine ("unknown ... state is a rejection,
  not a pass-through"). Fixed: the function now computes the set of raw
  (unvalidated) `chat.id` values across all inbound messages before any
  validation; if more than one distinct value exists, it raises
  `EnrollmentError` rather than guessing; otherwise it validates and
  returns the first message's `chat_id`.
- **C — the AST trust-boundary test was missing plan-mandated coverage.**
  `IMPLEMENTATION_PLAN.md`'s T16b section explicitly requires `discovery/`,
  `generation/`, `judging/` to never reach the sender, the bot token, *or*
  the enrolled `chat_id` — but Task 6 only renamed one constant
  (`waha_token` → `telegram_bot_token`) and never added `telegram_chat_id`
  to `FORBIDDEN_ATTRIBUTE_NAMES`. Separately, `personal_voice_msg.delivery`
  imports `send_voice_note` from `sender.py` but was never added to
  `FORBIDDEN_MODULES`, leaving a transitive path to the sender the test
  wouldn't catch. No live violation existed either way (confirmed by grep
  before and after) — this closed a coverage gap, not a real breach. Fixed:
  both entries added; the widened test still passes 3/3.

**6 Minor findings, triaged**:
- **D (deferred)** — the test-only `api_base` keyword-only parameter on
  `sender.py`/`delivery.py` has no production-side validation (unlike
  T15's loopback-validated `waha_base_url`). Not a `Settings` field, no
  production caller exists today, and adding a profile-based guard would
  require touching every `api_base`-using test fixture for no verified
  payoff against a non-reachable path. Left for a future task if a real
  production caller of `run_daily_send` is ever wired without going
  through this review again.
- **E (deferred)** — `database.py`'s `DELIVERY_TRANSITIONS[DELIVERY_UNKNOWN]`
  still permits `AUDIO_READY`/`SENT` edges left over from the deleted
  reconciliation subsystem; `delivery.py` never takes them (confirmed), so
  this is defense-in-depth only. Tightening it would require also
  rewriting a pre-existing, deliberately-written T16-era test
  (`test_delivery_state_machine.py`'s
  `test_delivery_unknown_can_transition_to_audio_ready_or_sent`) that is
  outside anything T16b's plan ever scoped to touch. Flagged for a future
  cleanup task (T18 or similar), not this branch's merge gate.
- **F (fixed, commit `e570e68`)** — a stale WAHA/reconciliation docstring
  in `test_delivery_window.py` describing already-deleted machinery;
  comment-only fix, no logic change.
- Three carried-over Task 7 minors (unchanged, still deferred): `_sent_count`
  doesn't explicitly close its SQLite connection; a pre-existing
  `_HangingServer` teardown race inherited from the security test file;
  `test_waha_deployment.py` is now permanently unsatisfiable but doesn't
  redden `-m security` (skip-gated); a stale `.gitignore` negation;
  `AGENTS.md`'s command list still referenced `docker compose config
  --quiet` (fixed by this task's own `AGENTS.md` update, see below).
- The security error-taxonomy suite (`test_sender_error_taxonomy.py`) is
  entirely skipped without `T13_VOICE_SAMPLE` — 11 of the 48 skips in the
  `-m security` run above. Defensible under the no-mock policy (real audio
  is needed to reach the network step), but this project's central
  fail-closed guarantee has not yet been exercised in a run with that env
  var set. Recorded here as an open verification gap for whenever a live
  environment is available, matching how T15's own e2e evidence gap was
  handled.

None of the deferred Minors are load-bearing for merge — each was traced
to either a genuinely unreachable path today, or scope that belongs to a
different, already-tracked task.
