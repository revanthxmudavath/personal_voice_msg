## Design summary

Full design: `docs/superpowers/specs/2026-08-24-t18-cloud-container-hardening-design.md`.
Full plan: `docs/superpowers/plans/2026-08-24-t18-cloud-container-hardening.md`.

Topology (human-confirmed during the pre-T18 reconciliation, restated in the
design spec's Context section): **one app container** (generation, judging,
voice/TTS, sender/delivery, scheduler — in-process, matching T15's own
precedent) plus **one discovery container/network**, since discovery
(untrusted web content, an LLM tool-use surface) is the actual trust boundary
in the current, post-T16b (Telegram) architecture — there is no WAHA/self-hosted
sender service left to isolate.

Two scope decisions made explicit at design time, both owner-confirmed:

1. **No cloud VPS exists for this project.** T18's own red tests (external
   port scan, WireGuard-only public firewall) only mean something against a
   real internet-facing host, which requires payment the agent cannot make.
   Resolution: build infra-as-code (`infra/firewall/rules.nft`,
   `infra/wireguard/wg0.conf.template`, `infra/ssh/sshd_config.d/10-hardening.conf`,
   `infra/RUNBOOK.md`), verify everything Docker Desktop can prove locally for
   real (a real throwaway Linux container's network namespace substitutes for
   "the host" in `tests/security/test_firewall_rules.py`), and defer the
   literal external-scan/live-firewall verification to the documented
   owner-run runbook step — the same split already used for T15's WAHA
   pairing and T17b's live STOP/send tests.
2. **The weekly discovery production pipeline has no caller anywhere in the
   codebase** — a pre-existing gap named by T17b's own design spec and
   explicitly deferred elsewhere, not built by T18. T18's discovery container
   needs a real bounded process to harden and fault-inject against, so it gets
   one (`discovery_worker_entrypoint.py` / `scripts/run_discovery_worker.py`)
   — explicitly a verification harness reusing T07's existing tested
   discovery code, not new production candidate-generation wiring.

### The one real failure — root-caused, not a code defect

`tests/security/test_firewall_rules.py::test_only_wireguard_udp_port_is_reachable_under_the_real_ruleset`
loads `infra/firewall/rules.nft` (via `nft -f`) inside a real throwaway Linux
container. It failed with `nft` syntax errors on every line
("unexpected junk"). Diagnosis, not guessed from the traceback alone:

1. `file infra/firewall/rules.nft` on the actual checked-out working copy
   reports **CRLF line terminators**. `git show HEAD:infra/firewall/rules.nft`
   (the committed blob) has **LF-only** line endings.
2. `git config --get core.autocrlf` (both repo-local and global, in this
   sandbox) is `true` — Git is rewriting the committed LF file to CRLF on
   checkout onto this Windows filesystem.
3. Manually reproduced both directions against the identical built fallback
   image (`t18-nft-verify-fallback:local`, the same image the test itself
   falls back to since `nixery.dev/nftables/iproute2/python3` has no `/bin/sh`
   in this environment, confirmed via the same smoke-test the test performs):
   - Mounting the actual on-disk (CRLF) file into the container reproduces the
     exact same `nft` syntax errors as the pytest failure, and the container
     exits before `_wait_until_running` succeeds.
   - Mounting a byte-identical copy with `\r\n` normalized back to `\n` (no
     other change) loads cleanly, and both the test's own negative control
     (curl against TCP 9999 times out with exit 28, confirming the firewall's
     default-drop policy) and positive control (a real UDP datagram to 51820
     gets echoed back `pong` through the loaded ruleset) pass.

This is a Windows-sandbox-only checkout artifact, not a defect in the
committed ruleset or in the T18 test logic itself — the real production target
(a Linux VPS, provisioned and deployed via `infra/RUNBOOK.md`) does not pass
this file through a Windows checkout with `core.autocrlf=true`, so this
failure mode cannot occur there. It also would not have been caught by Task
9's own implementer/reviewer, whose environment(s) evidently did not hit this
(per `progress.md`: "nixery.dev fallback image path exercised for real (both
implementer and reviewer's environments needed it)" with no CRLF note).
**Not fixed here** — this task's scope is documentation/verification only, no
code changes. Flagged for the controller/independent reviewer; a `.gitattributes`
entry forcing LF for `infra/firewall/rules.nft` (or the whole `infra/` tree)
would prevent recurrence for any future Windows-based contributor or CI runner
without changing the file's committed content.
