## Design decisions (restated from `IMPLEMENTATION_PLAN.md`'s T12 section
and made concrete here)

- **`message_rejections` table** (`SCHEMA_V5`, purely additive): `id`,
  `message_id INTEGER NOT NULL UNIQUE REFERENCES messages(id)`, `reason`,
  `rejected_at`. The `UNIQUE` constraint makes "exactly one rejection row
  per message" a real DB invariant, not just an application convention.
- **`Database._transition_message_in_transaction`**: the single-row
  compare-and-swap body of the existing `transition_message` was extracted
  into a private helper (same pattern as the pre-existing
  `_create_message_in_transaction`), so the new multi-step
  `reject_message`/`approve_message` methods can each run their whole
  operation — including the `DISCOVERED -> VALIDATED` step when needed — in
  one atomic transaction, not several separately-committed calls.
- **`Database.reject_message(message_id, reason, now)`**: atomically walks
  `DISCOVERED -> VALIDATED` if needed, then inserts the `message_rejections`
  row. Raises `InvalidTransition` if the message is already past
  `VALIDATED` (e.g. `QUEUED`), and `DatabaseInvariantError` on a second
  rejection attempt (via the `UNIQUE` constraint).
- **`Database.approve_message(message_id, now)`**: atomically walks the
  current state to `QUEUED` via the existing `CONTENT_TRANSITIONS` table.
  Raises `InvalidTransition` if already `QUEUED` or in any state outside
  `CONTENT_TRANSITIONS`.
- **`Database.next_unjudged_message()`**: oldest `DISCOVERED` or
  `VALIDATED`-without-a-rejection-row message, via
  `NOT EXISTS (SELECT 1 FROM message_rejections ...)`. A `VALIDATED`
  message with a rejection row is permanently excluded, which is what makes
  "never re-submitted to the judge" hold.
- **`Database.count_queued_messages()`**: plain count of `QUEUED` rows.
- **Reserve buffer = a computed threshold over `QUEUED` row count, not a
  new column/flag or separate pool.** `queue_refill.MIN_QUEUE_SIZE = 30`.
  `reserve_next_message` (T03, unchanged) already only ever draws from
  `QUEUED`, so "exhaustion selects only the pre-approved buffer" and "no
  buffer means no send" are properties of that existing method once refill
  is wired up — new tests exercise this at the orchestration level to lock
  it in as T12's own contract.
- **`queue_refill.refill_queue(database, session, api_key, now, target=30)`**:
  loops while `queued_count < target`, pulls the next unjudged candidate,
  runs `evaluate_message_safety`, and applies `approve_message` or
  `reject_message`. Stops without touching existing `QUEUED` rows when no
  candidates remain. Returns a `RefillResult(approved, rejected, health)`
  where `health: QueueHealth(queued_count, minimum, below_minimum)` is the
  computed queue-health signal.
- **"Queue-health alerts" scoped to the computed `QueueHealth` value only.**
  `IMPLEMENTATION_PLAN.md`'s T19 ("Audit, alerts, backups, and recovery")
  explicitly owns owner notification for queue exhaustion; wiring an actual
  alert channel now would be scope creep into a task that doesn't exist
  yet. T12 hands T19 a boolean it can act on.
- `EXPECTED_SCHEMA_V1_OBJECTS`'s live-`MessageState`-enum coupling (flagged
  in T11b) is **not** fixed here, per the plan: T12 does not add a new
  `MessageState` member, so it does not trigger the bug. Left for whichever
  future task does.

## Fast-test strategy for the safety pipeline (no live judge calls)

Following the exact technique already established in
`tests/fast/test_judging_pipeline_short_circuit.py`: gate-violating
candidate text makes `evaluate_message_safety` reject via the deterministic
gate before the judge is ever called, so `refill_queue`'s rejection path is
exercised with real code, a real (but never-dialled) `aiohttp.ClientSession`,
and a fake API key — no network call, no mock. The approval path is
independently covered elsewhere: `Database.approve_message` has its own
direct fast tests, and `decide_from_judge_result`'s `approved=True` branch
was already calibrated and tested in T11. `refill_queue`'s own
`if decision.approved` line is a one-line mirror of the (tested) rejection
branch; a further paid live end-to-end run was judged unnecessary scope for
this task, unlike T10/T11 where the LLM's own output behavior was what
needed calibrating.
