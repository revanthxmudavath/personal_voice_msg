## Two design decisions made explicit before coding (Karpathy guideline 1)

- **Pocket TTS synthesis interface resolved by reading the installed
  package's source, not guessed.** `TTSModel.get_state_for_audio_prompt()`
  detects a `.safetensors` path argument and loads it directly via its own
  internal `_import_model_state` — so T13's exported
  `voice_embedding.safetensors` feeds straight back in with no new
  import/deserialization code needed. `TTSModel.generate_audio(model_state,
  text) -> torch.Tensor` returns audio at `model.sample_rate`, confirmed at
  runtime to be a fixed 24000 Hz for the loaded English model.
- **T14 does not wire the long-dormant `audio_artifacts` table.** That
  table (`id`, `message_id`, `state`, `storage_key`, `expires_at`) has
  existed since schema V1 but no code has ever touched it. None of T14's
  four red tests need it, and its state vocabulary is undefined anywhere in
  the plan — wiring it now would be exactly the speculative-abstraction
  pattern T13 explicitly avoided for FFmpeg (`docs/task-logs/T13.md`,
  "Input format scope"). T14 needed no `database.py` changes at all:
  `transition_delivery`, `get_delivery_state`, and `reserve_next_message`
  (all pre-existing, T03/T12) already cover everything the plan's red tests
  require. How T15's sender locates the produced audio file is left as an
  explicit open note for T15, the same way T13 deferred FFmpeg-based input
  transcoding to T14.

## Real technical findings from building the format/signal validator

- **Ogg Opus containers always report the fixed 48000 Hz decode rate in
  their header regardless of encoding parameters** (RFC 7845) — confirmed
  by directly encoding a WAV with `ffmpeg -ar 8000 -c:a libopus ...` and
  reading the result back with `ffprobe`, which reported
  `"sample_rate": "48000"` anyway. A wrong-sample-rate defect can therefore
  only be caught on the **pre-encode WAV**, which is where `convert_to_opus`
  checks it, against Pocket TTS's confirmed `sample_rate` of 24000.
  `validate_audio`'s original sample-rate check against the final `.ogg`
  was removed as dead code that could never fire for a real Opus stream.
- **Truncating a valid `.ogg` file to 10% of its length was not reliably
  corrupt enough for `ffprobe` to fail on** (Ogg's page structure can still
  be partially readable). A fixed small-byte truncation (200 bytes,
  regardless of file size) reliably reproduces a real `ffprobe` parse
  failure.

## Two real Pocket TTS bugs found and fixed during owner listening review

The owner's first listening pass ("all under a second, quality not good")
surfaced two genuine defects in the synthesis path, not just parameter
tuning. Both are root-caused via `superpowers:systematic-debugging`
(traced into the library's actual generation loop, differential-tested
against a reference voice, never guessed) and fixed with their own
failing-test-first regression coverage.

1. **Premature end-of-speech detection.** Pocket TTS ships
   `DEFAULT_EOS_THRESHOLD = -4.0`, which detects end-of-speech almost
   immediately when conditioned on a cloned voice — confirmed by tracing
   into `TTSModel._autoregressive_generation`: `is_eos` fires within the
   first few generation steps, producing well under a second of audio for
   a multi-word sentence. A calibration sweep across multiple sentences and
   two voice embeddings (the cloned test voice and a built-in reference
   voice) found `eos_threshold=0.0` with `frames_after_eos=10` gives
   consistent, natural word rates (~2-3 words/sec) for short sentences.
   Fixed in `audio_pipeline.EOS_THRESHOLD` / `FRAMES_AFTER_EOS`, applied in
   `synthesize_to_wav` on every call (`model.eos_threshold = EOS_THRESHOLD`
   is set even for an injected model, so no caller can silently skip the
   calibration). Regression test:
   `test_synthesized_audio_is_not_truncated_by_premature_eos`.
2. **Untruncated >30s voice-conditioning prompt destabilizes EOS detection
   for longer sentences specifically.** The threshold fix above was
   calibrated on 10-12 word sentences and looked stable; testing it against
   longer sentences (17-20 words, per the owner's request for 5-10s clips)
   surfaced a second failure mode — most attempts hit Pocket TTS's own
   "Maximum generation length reached without EOS" ceiling (11-13s of
   likely garbage padding). A differential test against a built-in
   reference voice was stable at the same settings, isolating the problem
   to voice conditioning, not the threshold. T13's `enroll_voice` had been
   feeding the model the full untruncated 47-52s recording, exceeding
   Pocket TTS's own documented 30-second conditioning-prompt limit
   (`get_state_for_audio_prompt`'s own `truncate` parameter docstring).
   Truncating to 30s (`truncate=True`) fixed it outright. **This is a bug
   in already-merged T13 code**, found via T14's testing, fixed with its
   own red→green regression test
   (`test_synthesized_audio_is_stable_for_longer_sentences`, asserts no
   ceiling-warning via `caplog` and a plausible words/sec range) —
   confirmed T13's own existing enrollment tests still pass afterward.

## A third refinement, found during the owner's own manual listening (not
automated)

The owner judged voice-match quality directly by ear across several
rounds — decode-quality steps (`lsd_decode_steps` 1/4/8/16) made no
perceptible difference and were left at the library default; a real trial
of Chatterbox (MIT-licensed, the strongest fully-open alternative found by
web research) was **decisively worse** for this voice and not adopted (see
"Alternative TTS trial" below). What did help: inspecting the raw
recording's amplitude envelope found ~2.5s of near-silent lead-in at the
start (a common voice-memo artifact — pause before speaking), which meant
the 30-second truncation budget was spending ~2.5s on dead air instead of
real speech. Fixed generally, not as a one-off: `enroll_voice` now calls a
new `_trim_leading_silence` helper (pure function, scans 0.1s windows from
the start, returns audio from the first window at or above
`SILENCE_RMS_FLOOR`) before applying the 30s truncation, so any future
enrollment recording — including the owner's eventual real production
voice — gets its full 30s budget spent on actual speech. Covered by four
new `fast` unit tests on the pure function
(`tests/fast/test_voice_enrollment_trimming.py`); wiring re-verified
against T13's real integration suite. The owner's own A/B listening
(temperature 0.4 vs 0.7 on the trimmed clip, both beating the untrimmed
baseline) confirmed this was a genuine improvement, not a false lead.
Final pick: `temperature=0.7`, which is Pocket TTS's own library default —
no override needed in `synthesize_to_wav`.

## Alternative TTS trial (Chatterbox) — tried, not adopted

Owner asked to evaluate free/open-source alternatives after the voice
match still wasn't "exact" post-fix. Web research
(sources in-conversation) found Pocket TTS is architecturally a lightweight
edge model (sub-80ms latency, ~50MB), not built for maximum cloning
fidelity, and identified Chatterbox (Resemble AI, MIT license, CPU-capable)
as the strongest genuinely open-licensed alternative — XTTS v2 is CPML
(non-commercial only, and Coqui shut down in 2024 so no commercial license
path exists) and F5-TTS's original weights are CC-BY-NC-4.0, both failing
`AGENTS.md`'s open-source-or-openly-licensed constraint outright.

Ran a real trial: `uv run --with chatterbox-tts` (ephemeral, never added to
`pyproject.toml`/`uv.lock`), cloned the owner's voice from the same clean
recording, generated the same two comparison sentences. Hit and fixed a
real compatibility bug along the way — `resemble-perth` (Chatterbox's
watermarking dependency) imports the legacy `pkg_resources` API, which
current `setuptools` (v81+) no longer ships; needed `--with "setuptools<81"`
to construct the model at all. Despite that working, the owner's own
listening verdict was decisive: Pocket TTS was "much better." Not
adopted — no repository changes from this trial beyond the record here.
One open question surfaced but not resolved (moot given the outcome):
Chatterbox clones from the raw reference file at generation time with no
apparent equivalent to Pocket TTS's export-once-then-delete-the-source
enrollment flow, which would have been a real change to `AGENTS.md`'s
voice-privacy design had it been adopted.

## Implementation

New module `src/personal_voice_msg/audio_pipeline.py`:

- `AudioPipelineError(RuntimeError)` — single exception type, matching
  T13's `EnrollmentError` pattern.
- `synthesize_to_wav(embedding_path, text, destination, *, model=None)`:
  sets the calibrated `eos_threshold`, then real Pocket TTS
  `get_state_for_audio_prompt` + `generate_audio(..., frames_after_eos=10)`,
  written out via `soundfile` at `model.sample_rate`.
- `convert_to_opus(source_wav, destination)`: rejects a source WAV whose
  sample rate isn't Pocket TTS's `EXPECTED_SOURCE_SAMPLE_RATE = 24000`
  before ever invoking FFmpeg; otherwise a real `ffmpeg` subprocess call —
  `libopus`, mono, 48kHz, 24kbps, `-application voip` (the standard
  WhatsApp-voice-note encode target). Deletes any partial output file on a
  non-zero FFmpeg exit.
- `validate_audio(path)`: real `ffprobe` subprocess for format/codec/
  duration (`MAX_AUDIO_DURATION_SECONDS = 60.0`), plus a `soundfile`-decoded
  RMS/clipping check reusing T13's exact thresholds
  (`SILENCE_RMS_FLOOR = 0.001`, `CLIPPING_RATIO_CEILING = 0.01`) — this
  environment's `soundfile`/libsndfile build decodes Opus natively, so no
  second decode path was needed.
- `produce_voice_note(database, delivery_id, embedding_path, text,
  destination, now, *, model=None)`: orchestrates synthesize → convert →
  validate. Any exception at any step deletes the temp WAV and any partial
  `destination` file and re-raises, leaving the delivery's state untouched
  (still `RESERVED`) — this is what makes "failed synthesis leaves no
  sendable artifact" hold. On success, deletes the intermediate WAV and
  calls the existing `transition_delivery(delivery_id, AUDIO_READY, now)`.
- `remove_audio_after_delivery(database, delivery_id, audio_path)`: reads
  the delivery's current state via the existing `get_delivery_state` and
  refuses (raises `AudioPipelineError`) unless it is `SENT` — tested via
  real `transition_delivery` calls driving a delivery through
  `SENDING → SENT`, the same technique T12's tests already use to exercise
  state transitions without a real WAHA sender (which doesn't exist until
  T15).

Modified `src/personal_voice_msg/voice_enrollment.py` (T13 module, fixed
here — see "bugs found" above): `_trim_leading_silence` (new pure
function) + `enroll_voice` now trims leading near-silence and passes
`truncate=True` to `get_state_for_audio_prompt`.
