## Scope and task split

- T06 owns provider-neutral trusted-hit registration, a run-scoped private
  result-ID-to-URL map, and the secure `fetch_public_page(result_id)` transport.
- T07 owns the real SearXNG-backed `search_web(query)` request/parsing and
  Trafilatura extraction. It must register only results returned in that run
  through the T06 boundary.
- T09 owns any runtime discovery-agent benchmark. T06 gives deterministic or
  agentic callers the same narrow, enforceable web boundary.
- No agent-facing API accepts a URL. Full URLs remain private deterministic
  state; callers receive opaque random result IDs.
- Web metadata and fetched content remain untrusted. T06 does not extract,
  persist, approve, generate, synthesize, queue, or send content.

## Implemented boundary

- Added `aiohttp 3.14.2` as the smallest transport dependency and locked every
  transitive dependency.
- Search registration is atomic and limited to 20 results per run. Raw and
  sanitized title/snippet sizes are bounded, HTML is reduced to text, Unicode
  controls are removed, and all result IDs contain at least 192 bits of
  randomness.
- Result IDs are run-scoped and single-use. Fabricated, URL-shaped,
  cross-session, reused, closed-session, and concurrent requests fail with the
  same privacy-safe error.
- URL validation accepts only canonical public `http:80` and `https:443`
  destinations. It rejects credentials, fragments, non-default ports,
  ambiguous numeric forms, local suffixes, Unicode whitespace, controls, and
  non-public literal addresses.
- DNS resolution has a 3-second bound, rejects an answer set containing any
  non-public address, passes only validated numeric addresses to the connector,
  disables the connector DNS cache, revalidates the chosen socket address, and
  rejects a changed answer set during the fetch.
- Manual redirects enforce the same URL and DNS checks at every hop, reject
  loops and duplicates, permit at most five redirects, and reject HTTPS to HTTP
  downgrade.
- TLS uses the platform trust store while preserving the original hostname for
  HTTP Host and certificate verification even though the validated numeric
  address is dialed. Production explicitly passes that hostname as
  `server_hostname` for SNI.
- The client ignores ambient proxy variables, `.netrc`, cookies, and automatic
  decompression. It accepts only HTML, XHTML, or plain text and requires strict
  bounded headers and response framing.
- Bodies stream under a 1 MiB hard limit with a 15-second total deadline,
  3-second connect deadline, and 3-second idle-read deadline. A session permits
  only one in-flight fetch and cannot close during that operation.
- CI runs offline security tests normally and runs the real isolated network
  harness in a separate Docker job. Public live checks remain explicitly
  opt-in.

## Explicit residual limits and deferrals

- Python blocks the standardized NAT64 well-known and local-use prefixes, but a
  deployment-specific Pref64 cannot be inferred portably from an individual
  address. T18 must prohibit NAT64 on discovery networks or supply and test the
  deployment Pref64 before release, together with container egress controls
  that prevent discovery from reaching private services.
- An HTTP parser cannot treat bytes beyond a declared smaller Content-Length as
  part of that response. The client uses one request per forced-close connection
  so those bytes cannot be reused as another response; oversized declarations,
  premature EOF, transfer/content-length ambiguity, and streamed overflow are
  tested directly.
- DNS answer changes are tested directly against the same resolver instance and
  the production redirect path reuses that resolver. T18 still owns network
  policy and container egress enforcement.
- T07 must implement real SearXNG-backed `search_web(query)` and supply only
  results returned in that run through the trusted registration adapter; it
  must not add an arbitrary-URL path.
- Public live sites are useful compatibility checks but can change externally;
  only the deterministic Docker harness is a required CI gate.

## 2026-08-01 cloud SSRF and resource-limit remediation

The cumulative T01-T09 audit identified three remaining T06 evidence and
control gaps: Azure WireServer `168.63.129.16` was treated as globally public,
`FetchPolicy` accepted non-finite durations and non-integer count limits, and
the DNS-change test invoked `_PublicResolver` directly instead of proving the
behavior through a real redirect and connector path.

Initial red evidence:

- The deterministic boundary suite reported `39 failed, 22 passed`. Literal
  Azure registration and `is_public_address()` were accepted. All five
  byte/count fields accepted positive floats, booleans, NaN, or positive
  infinity, and all four duration fields accepted NaN or positive infinity.
- The first rebuilt isolated Docker run reported `1 failed, 30 passed` because
  a redirect reached the canary bound to `168.63.129.16` instead of being
  rejected before the destination request.

The production boundary now has an explicit cloud-platform address deny set
containing `168.63.129.16`. Because `is_public_address()` is shared by literal
URL canonicalization, DNS-answer validation, redirects, and the socket factory,
the address is denied consistently at every connection path.

`FetchPolicy` validates its fields in two groups:

- byte and count limits must have exact positive `int` values, excluding
  booleans and every float representation;
- time limits must be positive finite `int` or `float` values, excluding
  booleans, NaN, and positive or negative infinity.

The Docker harness now includes an Azure canary on an isolated
`168.63.129.0/24` network and a real DNS-rebinding flow. The first request
resolves to and reaches the permitted public fixture, which waits before
returning a redirect. The runner changes the operating-system name-service
answer, then releases the response. Aiohttp's forced-new connection and
disabled DNS cache cause production `_PublicResolver` to see the changed
answer set and reject it. The changed destination's counter remains unchanged.
The test never calls `_PublicResolver` directly.

An independent read-only security review found one blocking false-positive in
the first version of this test: `/rebound` returned 404 on the original public
fixture, so stale DNS could mimic the expected generic rejection. The accepted
fix makes `/rebound` a valid supported 200 response on the original fixture.
Cached DNS, connection reuse, or skipped re-resolution therefore makes the
test fail by succeeding; contacting the changed destination increments its
canary. The rebuilt Docker suite passed all `31` cases. The independent
re-review confirmed the proof is sound and found no remaining blocking issue.
