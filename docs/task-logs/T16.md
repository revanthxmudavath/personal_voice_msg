## Design: `reconcile_delivery`

`reconcile_delivery(session, settings, attempt_window_start, now)` fetches
the most recent `RECONCILE_MESSAGE_LIMIT` messages from the recipient's
chat and scans them for a `fromMe=true`, `hasMedia=true`,
`media.mimetype` starting with `"audio/"` message whose `timestamp` is at
or after `attempt_window_start`. WAHA gives no client-supplied idempotent
id to dedupe a send against (unlike `sender_auth_nonces`, which only
protects the *request*, not WAHA's own processing of it), so this scan
against WAHA's own chat history is the only way to resolve a
`SenderAmbiguous` outcome.

Three outcomes, matching `DELIVERY_TRANSITIONS[MessageState.DELIVERY_UNKNOWN]
== {AUDIO_READY, SENT}` in `database.py`:

- A matching message is found → `(MessageState.SENT, provider_message_id)`
  (`provider_message_id` from `_data.key.id`), regardless of elapsed time.
- No matching message, and the query itself succeeded (a real, well-formed
  answer from WAHA) and enough time (`RECONCILE_GRACE_SECONDS`) has passed
  since `attempt_window_start` that a real send would already have shown
  up in chat history → `(MessageState.AUDIO_READY, None)`, i.e. "conclude
  it was never sent, safe to retry from audio-ready."
- Anything else — no matching message but not enough time has passed yet,
  *or* the WAHA query itself failed/errored/was malformed — →
  `(MessageState.DELIVERY_UNKNOWN, None)`. This is the fail-closed branch:
  a WAHA-side failure while reconciling must never be silently treated as
  "conclusively not sent," since `DELIVERY_UNKNOWN` is not itself a legal
  transition target from `DELIVERY_UNKNOWN`
  (`database.py`'s `record_delivery_attempt` raises `InvalidTransition` if
  a caller tries). **Callers (Task 8's `delivery.py` orchestrator) must
  check for this sentinel explicitly and skip calling
  `record_delivery_attempt` entirely when it's returned — not pass it
  through as if it were a normal transition target.** This is documented
  directly in `reconcile_delivery`'s docstring in `sender.py`.

`RECONCILE_GRACE_SECONDS` is set relative to `REQUEST_TIMEOUT_SECONDS`
(the same 30s bound `send_voice_note`'s own WAHA call is subject to): a
real send either completes or times out within `REQUEST_TIMEOUT_SECONDS`,
so once more than that has elapsed since `attempt_window_start` with
nothing in chat history, the original request is conclusively over and
its outcome (never reached WAHA, or reached WAHA but failed) is already
decided — nothing will appear later. A margin above the raw timeout
absorbs WAHA-side echo/indexing latency.

## A real gap this task's own tooling caught (not from review — from running it)

### 1. WAHA chat-history indexing lag is real, not instantaneous

The first red-then-green pass wrote `reconcile_delivery` as a single
GET-then-scan with no retry, following the brief's sketch literally. The
first real run against the live session (`send_voice_note` immediately
followed by `reconcile_delivery` in the same test) returned
`DELIVERY_UNKNOWN` instead of the expected `SENT` — the just-sent message
was not yet visible via `GET .../messages` right after `sendVoice`
returned. Measured directly (send a real voice note, then poll
`.../messages` in a tight loop, timing when the sent message's
`_data.key.id` first appears): **indexing lag after send completion was
observed in the 0.5s–1.3s range across repeated real runs, with one
colder-state outlier around 3.5s.** This is a real WAHA/NOWEB-store
characteristic (the send confirmation from WhatsApp and the local NOWEB
store index are not the same event), not a bug in the query logic.

Fix: `reconcile_delivery` now retries the chat-history query internally —
`RECONCILE_POLL_ATTEMPTS = 3` attempts, `RECONCILE_POLL_DELAY_SECONDS =
1.0` apart (up to ~2s extra) — before falling through to the
`RECONCILE_GRACE_SECONDS`-gated no-match outcome. This is deliberately
small: it smooths the common sub-2s case, but `reconcile_delivery` is not
meant to block for a long time on a single call (Task 8's orchestrator
needs to call it repeatedly and cheaply), so it does not try to guarantee
finding a just-sent message within one call. A hard query failure (bad
HTTP status, network error, malformed/oversized/non-list JSON)
short-circuits straight to `DELIVERY_UNKNOWN` without retrying — that's a
WAHA-reachability problem, not an indexing-lag problem, and internally
retrying it would just delay an already-known "unknown" answer while
adding no new information.

A first attempt at this fix used a much larger internal retry budget (5
attempts, 1.5s apart, ~6s total) sized off single, isolated
send-then-poll measurements. Under this task's own testing conditions —
many real voice notes sent back-to-back in quick succession while
probing/diagnosing — that budget was repeatedly insufficient: one
diagnostic run needed **well over 6s and up to and beyond 30s** of actual
caller-side retrying before the just-sent message became queryable,
confirmed by directly polling `.../messages` afterward and finding it had
in fact arrived, just later than any single-call budget could reasonably
wait for. This traces to real backlog from this task's own rapid
back-to-back sends to the same real WhatsApp number/session — not
representative of this application's actual one-voice-note-per-day
production cadence, and not something `reconcile_delivery` should be
sized around absorbing internally. The correct fix was architectural, not
a bigger number: shrink the internal poll back down to the "smooth the
common case" size, and make the *caller* (both the test and, later,
Task 8's orchestrator) responsible for retrying the whole
`reconcile_delivery` call on `DELIVERY_UNKNOWN` — exactly the contract
the function's docstring already specifies. `tests/e2e/test_reconciliation.py`'s
`SENT`-outcome test now plays that caller role directly (bounded retry
loop, comfortably under `RECONCILE_GRACE_SECONDS` so a genuine failure
still fails loudly instead of silently drifting into the `AUDIO_READY`
branch).

### 2. Shared, persistent real chat history breaks a window keyed off wall-clock offsets

The brief's sketch for the "no send in this window" test used
`attempt_window_start = now - timedelta(minutes=10)`. Against a shared,
persistent real WhatsApp chat (this session has already sent real
messages in prior T15/T16 runs, and this file's own `SENT`-outcome test
sends one first), a 10-minute lookback window is not actually empty —
the first real run returned `SENT` for this test because it matched an
unrelated real voice note sent minutes earlier by the preceding test in
the same file. `reconcile_delivery` was working correctly; the test's
assumption ("this window is empty") was false against the real,
never-cleared chat history.

Fix: anchor `attempt_window_start` at the test's own current invocation
time (`datetime.now(UTC)`, taken *after* any earlier test's real send has
already completed and been timestamped), not at a fixed offset into a
history that other tests and other task runs keep adding real messages
to. Grace-period elapse is then simulated purely through the `now`
argument (`attempt_window_start + timedelta(seconds=RECONCILE_GRACE_SECONDS
+ 5)`), so the test doesn't need to sleep 45+ real seconds to prove the
elapsed-time branch. The `SENT`-outcome test already matches on the exact
`provider_message_id` its own `send_voice_note` call returned, so it was
never at risk of a false positive from unrelated chat history — only the
no-send test's window needed this fix.

### 3. Independent re-verification found real flakiness at the 30s caller-retry budget — the real cause was worse than initially estimated

The controller independently re-ran `tests/e2e/test_reconciliation.py`
after this task's first commit (`424ac53`) and got `1 failed, 2 passed`
(`test_reconcile_delivery_finds_a_message_that_was_actually_sent` failed
with `DELIVERY_UNKNOWN` instead of `SENT`), contradicting this task's
own reported "3/3 passed" from two earlier clean runs. Investigated
properly per the controller's request rather than re-running until green:

**Step 1 — 5 individual timed runs of just the `SENT`-outcome test**
(`--durations=0`, isolating the "call" phase — the real send + reconcile
work — from the ~15-18s `valid_audio_bytes` fixture setup), at the
original `_CALLER_RETRY_BUDGET_SECONDS = 30.0`:

| run | outcome | "call" duration |
|---|---|---|
| 1 | PASS | 1.46s |
| 2 | PASS | 1.84s |
| 3 | **FAIL** | 31.62s (never resolved within the 30s budget) |
| 4 | PASS | 1.99s |
| 5 | **FAIL** | 33.01s (never resolved within the 30s budget) |

2/5 (40%) failed to resolve within the 30s budget. A direct chat-history
check immediately afterward confirmed **both "failed" messages had in
fact been indexed by WAHA by the time of that later check** — this is
lag, not lost data — but the exact resolution time for those two beyond
~31-33s was not captured, since the test itself stopped polling at the
budget.

**Step 2 — isolated tail-latency diagnostics** (send once, poll up to
90-120s, outside the pytest fixture/test-retry machinery): three
separate isolated sends all resolved in 3.4-3.6s. This initially
suggested the 30-33s failures were anomalies specific to the tighter
pytest-run cadence, not a stable characteristic — and also ruled out a
suspected clock-skew bug (`docker exec ... date -u +%s` vs. host `date -u
+%s` were in sync at check time; a live instrumented replica of
`reconcile_delivery`'s own timestamp filter, run immediately after,
showed a correctly-ordered, small positive timestamp delta with the
message found on the very next poll — so the `timestamp < window_start`
filter itself is not the cause).

**Step 3 — widened `_CALLER_RETRY_BUDGET_SECONDS` to 40.0** (real
empirical margin over the two measured 30s-budget failures, still under
`RECONCILE_GRACE_SECONDS`), then re-ran the full file 5 times as
instructed:

| run | outcome | "call" duration (SENT test) |
|---|---|---|
| 1 | PASS | fast (~29.95s total file time, consistent with a ~1-2s call) |
| 2 | **FAIL** | ~40s+ (70.96s total file time) |
| 3 | **FAIL** | 43.67s |
| 4 | **FAIL** | 44.22s |
| 5 | **FAIL** | 44.91s |

4/5 failed at the *widened* 40s budget, with the observed "call"
duration **climbing on each successive run** (43.67s → 44.22s → 44.91s)
— approaching `RECONCILE_GRACE_SECONDS` (45s) itself. This is not random
noise around a stable mean; it reads as a real, worsening backlog on the
WAHA/WhatsApp side, most plausibly caused by this task's own cumulative
testing load on the same real WhatsApp test session (dozens of real
voice notes sent across this task's diagnostics, timing probes, and
multiple full-suite re-runs within roughly 90 minutes). `docker stats`
showed no container-side resource pressure (0.11% CPU, 378MiB/7.58GiB
memory) at the time, consistent with the bottleneck being external
(WhatsApp-side echo/read-receipt processing or NOWEB-store indexing
catching up), not a local resource exhaustion this repo's tooling could
fix.

**Conclusion, per the controller's own decision criteria**: this is the
"5 consecutive real runs still show worrying variance even after
widening the test budget" case. `_CALLER_RETRY_BUDGET_SECONDS` is kept
at the data-justified `40.0` (real, measured improvement over the
original `30.0`, still meaningfully under the 45s production ceiling per
the existing design constraint) — but no further widening was attempted,
because the data shows indexing lag tracking toward and past 40s under
sustained load, i.e. a larger test-side number does not solve this and
risks colliding with `RECONCILE_GRACE_SECONDS` itself. **`RECONCILE_GRACE_SECONDS`
(45s, a production constant in `sender.py`, not modified by this fix) is
flagged as a real, open concern**: if real WAHA indexing lag can reach
~45s under load (as observed here), a production delivery that really
did succeed could be incorrectly concluded `AUDIO_READY` ("never sent")
before WAHA's own record catches up, and Task 8's orchestrator could then
resend — the exact duplicate-delivery failure mode T16 exists to
prevent. This was not fixed here (changing a production constant based
on data gathered under this task's own self-inflicted heavy load, without
the owner's or Task 8's design input, was judged out of this task's
scope and riskier than leaving it flagged) — **Task 8's orchestrator
design should treat this as a known, evidenced risk, not a hypothetical
one**, and should consider either a larger production grace period, a
persisted/cross-call retry count instead of a single elapsed-time
threshold, or confirming with the owner whether this session's observed
degradation was itself an artifact of unusually heavy synthetic test
traffic rather than representative of real one-message-per-day usage
(the latter is plausible but not proven — this task did not have a way
to test the "cooled down, lightly used session" case without further
adding to the same load it was trying to measure around).

## 4. Task review found a real, distinct fail-closed gap: malformed matching-message shape silently treated as "not a match"

Independent task review (told explicitly not to re-litigate the
already-accepted WAHA-indexing-lag risk above, and correctly didn't) traced
every path in `_fetch_matching_provider_id`'s scan loop and found a real
gap independent of the timing issue, confirmed against current source
before being escalated:

```python
timestamp = message.get("timestamp")
if not isinstance(timestamp, int | float):
    continue                              # <- silently treated as "no match"
...
try:
    return str(message["_data"]["key"]["id"])
except (KeyError, TypeError):
    continue                              # <- silently treated as "no match"
```

Once a message has already passed the substantive filters (`fromMe is
True`, `hasMedia is True`, `media.mimetype` starts `"audio/"`) -- i.e.
WAHA is clearly telling us "this is an outgoing voice note" -- a
malformed/missing `timestamp` or `_data.key.id` on *that same message*
was being treated identically to "this message simply isn't a match,"
via a plain `continue`. If that happened on every candidate message
across all `RECONCILE_POLL_ATTEMPTS`, and the caller was past
`RECONCILE_GRACE_SECONDS`, `reconcile_delivery` would conclude
`(MessageState.AUDIO_READY, None)` for a delivery that in fact already
happened -- a duplicate-send outcome, the exact failure T16 exists to
prevent, and one that completely bypassed the existing
`_ReconcileQueryFailed` -> `DELIVERY_UNKNOWN` fail-closed path since no
exception was ever raised.

**Fix**: once a message has passed the `fromMe`/`hasMedia`/audio-`mimetype`
gates, a malformed/missing `timestamp` or `_data.key.id` on that specific
message now raises `_ReconcileQueryFailed` (-> `DELIVERY_UNKNOWN`), not
`continue`. A message that fails those substantive gates in the first
place is still genuinely not a candidate and still just `continue`s --
the escalation is scoped precisely to "WAHA already told us this one
matters."

**Testability, and why this didn't need another real WAHA call**: the
finding is about response-*shape* handling, not real WAHA timing
behavior, and the review explicitly suggested testing at the lowest
level that proves it, to avoid adding more real-send traffic to the
already-flagged, heavily-loaded shared staging session. The scanning
loop was extracted into a new pure, synchronous function,
`_find_matching_provider_id(messages: object, window_start_timestamp:
float) -> str | None` -- no network I/O, no aiohttp session, just the
same scan logic operating on an already-parsed payload.
`_fetch_matching_provider_id` now does only the real HTTP GET + JSON
parse, then delegates to it. This is not a mock of anything (no
external system, LLM, WhatsApp, or DB is faked) -- it's the same
no-mock-policy-compliant pattern already used for `sign_request`/
`verify_signature`/`is_fresh` elsewhere in this file: pure logic
extracted so it can be unit-tested with real Python data directly.
`tests/fast/test_reconcile_matching.py` (new, `-m fast`) covers: a
well-formed match; multiple genuinely-non-candidate shapes correctly
still returning `None`; a match before the window being skipped; finding
the right message after skipping a non-candidate; a non-list payload
raising; a malformed timestamp (`None`, a string, a list, a dict) on an
otherwise-matching message raising (parametrized, the review's exact
finding); a missing `_data.key.id` on an otherwise-matching message
raising; and -- to prove the escalation is correctly scoped, not
over-broad -- a non-candidate message with a garbage timestamp still
just being skipped rather than raising, with the real match after it
still found.
