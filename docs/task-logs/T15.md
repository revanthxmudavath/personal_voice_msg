## Resolved design decision: audio location

T14 left open how T15's sender locates the audio file for a given delivery
(`audio_artifacts` unwired; `produce_voice_note` takes a caller-supplied
`destination: Path`). Re-reading `IMPLEMENTATION_PLAN.md`'s own T15
implementation line resolves this directly:

> "Add a narrow sender accepting validated audio bytes and an idempotency key."

The sender's interface takes audio **bytes**, not a `delivery_id` to look
up. Whatever calls the sender (this task's test harness now; T16's
orchestrator later) calls T14's `produce_voice_note` first and passes the
resulting bytes straight through in the same call. This needed neither of
the two options the task brief offered:

- (a) wiring `audio_artifacts` with the produced path — an unneeded DB
  write, and the table's state vocabulary is still undefined anywhere in
  the plan (same reasoning T14 already recorded for leaving it unwired).
- (b) a deterministic path convention derived from `delivery_id` — an
  unneeded filesystem coupling.

Both would have been speculative abstraction the sender doesn't need
(Karpathy guideline 2). No `database.py` change was required for this
specific question (a `SCHEMA_V6` change is still needed for a different
reason — replay-protection nonces, see below).

## Design: sender boundary architecture

Full brainstormed design, approved by the owner before implementation:

**WAHA deployment** — new `docker-compose.yml`, `devlikeapro/waha`
(Core, MIT-licensed) pinned to a real dated tag (not `latest`), NOWEB
engine (no headless browser). Port bound to `127.0.0.1:3000:3000` only
(WAHA's own documented default pattern) — never `0.0.0.0`, which is what
makes "no public dashboard or API exposure" true while still allowing the
one-time QR pairing and the sender's local calls. `WAHA_API_KEY` set to
the same value as T02's `waha_token_file`, plus dashboard/swagger
username+password for defense-in-depth. Secrets supplied via a git-ignored
`.env` file (`.env`/`.env.*` already in `.gitignore`), never in the
compose file itself. Session data in a named Docker volume, not a repo
bind mount.

**`src/personal_voice_msg/sender.py`** (new) — one function,
`send_voice_note(database, settings, audio_bytes, idempotency_key,
timestamp, signature, now) -> str`. No recipient parameter exists at all
— the recipient is structurally always `settings.recipient`. Checks, in
order, all fail-closed, all before any WAHA call:

1. HMAC-SHA256 signature check (`hmac.compare_digest`) over
   `f"{timestamp}:{idempotency_key}"`, keyed by a new secret
   `sender_auth_key`.
2. Freshness check: `abs(now - timestamp) <= 300s`.
3. Replay check: atomic SQLite insert of `(idempotency_key, timestamp)`
   into a new table; a duplicate raises immediately.
4. Audio validity: write bytes to a temp file, reuse T14's real
   `audio_pipeline.validate_audio`.
5. Only then: real `POST {waha_base_url}/api/sendVoice` with `chatId`
   derived from `settings.recipient.reveal()`, `X-Api-Key:
   settings.waha_token.reveal()`, `file: {mimetype: "audio/ogg;
   codecs=opus", data: base64(audio_bytes)}` — no WAHA-side re-encoding,
   since T14 already produces WhatsApp-ready Opus.

**`config.py` extension** (T02's file, additive only) — two new fields,
following the exact existing pattern: `waha_base_url: str` (new plain,
non-secret TOML setting, validated loopback-only for now; production's
real URL is T18's concern) and `sender_auth_key: SensitiveValue[str]` (new
secret file, parsed exactly like `waha_token` is today, added to
`redactor()`).

**`database.py` extension** (T03's file, additive `SCHEMA_V6`) — one new
table, `sender_auth_nonces(idempotency_key, timestamp, expires_at)` with a
uniqueness constraint on `(idempotency_key, timestamp)`, plus one new
method `record_sender_nonce(...)` that raises on a duplicate insert. This
is authentication-layer replay protection only — explicitly not T16's
exactly-once delivery/retry bookkeeping (persisting WAHA message
identifiers and attempt records), which stays out of scope here.

**"Discovery/model/TTS cannot call WAHA directly"** — extends T13's real
AST-based test (`tests/security/test_voice_enrollment_boundaries.py`) to
also forbid `discovery/`, `generation/`, `judging/` from importing
`personal_voice_msg.sender` or referencing the new `sender_auth_key`/
`waha_token` attributes. This is exactly what AGENTS.md's T13 entry
already flagged this test as needing to do when T15 built the sender.
Real network isolation between components stays T18's job (confirmed with
the owner rather than assumed — T15 builds an in-process module with a
real, tested authentication boundary; T18 owns the container/network
hardening that would make that boundary a real network boundary too).

## Implementation

TDD throughout: each behavior below has a real red test (verified failing
for the intended reason) before its implementation, except two small,
tightly-scoped defensive branches inside `_waha_base_url`/`_sender_auth_key`
that were written alongside the one happy-path test already TDD'd for
loading, matching this file's own established style where a parser bakes
in its own validation (`_token`, `_recipient`) — those branches were then
pinned with their own tests immediately after, and one (`?query=`/`/path`
rejection) genuinely caught a real gap on first run.

**`src/personal_voice_msg/config.py`** (T02's file, additive): two new
`Settings` fields — `waha_base_url: str` (plain, loopback-only, validated
scheme/host/no-extra-components) and `sender_auth_key: SensitiveValue[str]`
(new secret file, parsed like `waha_token`), both wired into `redactor()`.

**`src/personal_voice_msg/database.py`** (T03's file, additive
`SCHEMA_V6`): new `sender_auth_nonces(idempotency_key, timestamp,
expires_at)` table with a `(idempotency_key, timestamp)` uniqueness
constraint, plus `Database.record_sender_nonce(...)` which raises the new
`ReplayDetected` on a duplicate insert. Migration correctly threads through
the existing version-set machinery (V4→V5 now inserts literal `5`, not
`CURRENT_SCHEMA_VERSION`, so a new V5→V6 step could be added cleanly).

**`src/personal_voice_msg/sender.py`** (new): `sign_request`/
`verify_signature` (HMAC-SHA256 over `f"{timestamp}:{idempotency_key}"`,
constant-time compare), `is_fresh` (300s replay window), and
`send_voice_note(session, database, settings, audio_bytes, idempotency_key,
timestamp, signature, now) -> str`. No parameter can select a recipient —
the destination is always `settings.recipient`. Order: signature → freshness
→ replay (real SQLite insert) → audio validation (reuses T14's real
`audio_pipeline.validate_audio`) → real WAHA `POST /api/sendVoice`. Any
failure before the WAHA call makes zero WAHA calls. Follows the exact async
`aiohttp` pattern already established in `generation/gemini_client.py`
(bounded response reading, disabled redirects, narrow exception mapping).

**`tests/security/test_voice_enrollment_boundaries.py`** (T13's file):
extended `FORBIDDEN_MODULES`/`FORBIDDEN_ATTRIBUTE_NAMES` to also cover
`personal_voice_msg.sender`, `sender_auth_key`, and `waha_token` — exactly
what AGENTS.md's T13 entry flagged this file as needing when T15 built the
sender. This is preventive coverage (nothing in `discovery/`, `generation/`,
or `judging/` currently violates it), not a reactive fix.

**`docker-compose.yml`** (new, repo root): `devlikeapro/waha` (WAHA Core,
MIT-licensed — verified, not `waha-plus`), pinned to
`noweb-2026.7.2@sha256:33ecd1b782b2708db2ff1d366f51608889a036e76332dceae3fbbe3f10f2d75e`
(a real, dated tag resolved by `docker pull` + `docker inspect`, not
`latest`). Port `127.0.0.1:3000:3000` — WAHA's own documented default
pattern, loopback-only. `WAHA_API_KEY`/`WAHA_DASHBOARD_USERNAME`/
`WAHA_DASHBOARD_PASSWORD`/`WHATSAPP_SWAGGER_USERNAME`/
`WHATSAPP_SWAGGER_PASSWORD` required via Compose's `${VAR:?}` syntax,
sourced from a git-ignored `.env` (template at `.env.example`, already
covered by the repo's existing `.env`/`.env.*` gitignore rule). Session data
in a named volume, not a repo bind mount.

**`scripts/repository_policy.py`** (small, additive): filename-based
detection extended with `"sender" in filename and "key" in filename`,
closing the forward-note left by `docs/task-logs/T02.md` ("provider-specific
WAHA token-content detection is deferred until T15 defines the credential
format"). Investigated content-based detection too: unlike Gemini keys
(fixed `AIza`-prefix) or GitHub tokens (fixed `ghp_`/`github_pat_` prefix),
WAHA imposes no fixed token format at all, so no equivalent content regex is
possible — filename-based detection (already this repo's approach for WAHA
tokens/sessions since T01/T02) remains the only mechanism, now extended to
the sender's own key.

**`README.md`**: one-line factual correction — the "Configuration boundary"
section said the non-secret TOML contains only a profile, secret root, and
secret-file names; it now also correctly mentions the plain
`waha_base_url` and the new `sender_auth_key` secret.

## A real gap this task's own tooling caught (not from review — from running it)

Local dev secrets (a real phone number, generated WAHA/sender-auth keys, a
real voice embedding) were initially placed in a new `dev-config/` directory
*inside* the repository, added to `.gitignore`. Git itself would never have
committed it. But `scripts/repository_policy.py`'s secret scanner
deliberately does **not** trust `.gitignore` -- it walks the filesystem
against its own hardcoded `EXCLUDED_DIRECTORIES` allowlist (`.venv`,
`node_modules`, etc.) precisely so a wrong or incomplete ignore rule can
never silently exempt something. It correctly flagged every file under
`dev-config/secrets/`. Fix: moved the whole directory to
`F:\personal_voice_msg-dev-config` (a sibling of the repo, matching how
`F:\test_voice.wav` was already kept outside the repo since T13) rather
than weakening the scanner's coverage. `scripts/repository_policy.py all
--root .` is clean afterward. No repository-policy exemption was added for
`dev-config` -- the scanner's independence from `.gitignore` is exactly the
property that caught this, and weakening it would have defeated that.

## Independent review

Required (T15 is on AGENTS.md's mandatory list: T06, T15, T16, T17, T18).
Performed by a fresh `general-purpose` subagent with no implementation
context -- given only `AGENTS.md`, `IMPLEMENTATION_PLAN.md`'s T15 section,
this task log, and the diff, and told to verify the log's claims against
actual source rather than trust them.

**Result: no high-confidence (>=8) vulnerabilities.** The reviewer traced,
against real source (not the task log's prose): recipient redirection
(structurally impossible -- no recipient-shaped parameter exists anywhere
in `send_voice_note`), HMAC signature binding (checked for a
`timestamp:idempotency_key` delimiter-collision attack specifically --
none possible, since a pure-digit timestamp can never contain the `:`
separator), replay-protection atomicity (confirmed `record_sender_nonce`
runs inside `BEGIN IMMEDIATE`, ruling out a check-then-insert race, not
just trusting the unique constraint alone), `waha_base_url` SSRF (tested
parser-confusion patterns -- userinfo tricks, embedded-host tricks --
against the actual allowlist validator; none bypass it), and confirmed
`sender_auth_key` is never logged or embedded in any exception message.
One informational-only note: `repository_policy.py`'s new filename rule
(`"sender" in filename and "key" in filename`) can be evaded by a secret
saved under an unrelated filename -- explicitly flagged as mirroring the
already-accepted `waha_token` pattern and not graded as a finding (matches
this task's own "no fixed content format" limitation, documented above).

The reviewer flagged three things it could not verify itself (no Docker
access, no access to this session's real paired WAHA session) -- closed
here with evidence already gathered independently of the reviewer:
- **Real container port binding**: `docker inspect
  personal_voice_msg-waha-1` showed `{"3000/tcp":[{"HostIp":"127.0.0.1",
  "HostPort":"3000"}]}` -- also directly asserted by
  `test_waha_container_publishes_no_public_port`, run and passed against
  the live container (see Verification).
- **`WAHA_API_KEY` actually gates the API**: real unauthenticated `curl`
  requests to `/api/sessions` and `/dashboard` both returned `401` before
  any test was written; `test_waha_rejects_unauthenticated_requests`
  pins this.
- **E2e evidence is self-reported**: true of the automated test output,
  but the two real voice-note deliveries were independently confirmed by
  the owner in chat ("connected", "yup! I got it"), not only by my own
  test run's exit code.
